## 1. 背景：为什么需要超节点

### 1.1 算力需求的指数增长

前沿 AI 模型的训练算力需求呈稳定指数增长。从 2020 年 GPT-3（约 3.14 × 10²³ FLOPs）到 2025 年 Grok-3（约 3.5 × 10²⁶ FLOPs），5 年间增长超过三个数量级。Kaplan et al. (2020) 提出的 Scaling Law 表明，模型性能与训练计算量之间存在幂律关系——要获得可感知的性能提升，所需计算量必须按固定比例增长，且这条幂律没有收敛迹象。

与此同时，模型架构本身也在向"通信密集"方向演进。2024-2025 年间，以 DeepSeek-V2/V3 为代表的 MoE（Mixture of Experts）架构在前沿模型中全面铺开，从根本上改变了 Scale-Up 域的通信需求画像：

| 维度 | Dense/TP 时代 | MoE/EP 时代 |
| --- | --- | --- |
| 主要通信模式 | AllReduce, AllGather | All-to-All（动态路由） |
| 流量可预测性 | 高（同步、对称） | 低（稀疏、动态、非对称） |
| 带宽敏感性 | 高（梯度同步） | 极高（每层每 token 均需路由） |
| 延迟敏感性 | 中（可隐藏） | 极高（EP 路由在关键路径上） |
| 尾延迟容忍度 | 可接受 | 极低（一个慢专家拖慢全局） |

EP 通信对带宽、延迟和动态调度能力的三重极端要求，使得传统网络的性能天花板成为模型训练效率的核心瓶颈，倒逼产业界进行全栈重构。

### 1.2 制程红利放缓与系统级增长

单芯片制程红利通常只能支撑约每两年 **2.5 倍** 的增长，而国际领先平台在系统层面却实现了约每两年 **5-6 倍** 的算力跃升。系统增速显然不能仅用摩尔定律的延续来解释。

更合理的答案是到系统层去寻找：每一代都在**封装、互联、内存、精度、软件和整机工程**等维度引入新的设计变量，使原本不可同时达到的一组性能、成本与复杂度组合变得可达，并推动系统能力边界持续外移。

### 1.3 超节点的定义

超节点（SuperPod）不是"把更多卡装进一个机柜"的工程放大版。更准确地说，它是**局部性边界被重新定义后的系统对象**：试图把更多高价值通信、远端访存、同步协同和恢复控制稳定收敛在同一个受控域内，这个域既要低时延、低抖动，也要具备可维持内存语义或近内存语义、故障域可控并最终兑现 Goodput 的能力。

三个扩展层次的划分：

| 层次 | 含义 | 典型技术 |
| --- | --- | --- |
| **Scale-Up** | 高带宽域内统一寻址、原子操作、近内存语义 | NVLink/NVSwitch、UB 灵衢、HCCS |
| **Scale-Out** | 节点或超节点横向扩展为更大集群 | RoCE/RDMA、InfiniBand |
| **Scale-Across** | 跨园区、跨中心、跨资源域协同 | DCN、广域互联 |

超节点的核心价值在于：**把尽可能多的高价值通信稳定留在 Scale-Up 受控域内**，而非依赖延迟更高、抖动更大的 Scale-Out 网络。

### 1.4 华为的战略选择

在 2025 年 9 月华为全联接大会上，华为轮值董事长徐直军明确阐述了华为的算力战略：

> "由于我们受到美国的制裁，不能到台积电去投片，我们单颗芯片的算力相比英伟达是有差距的。但是华为有三十多年联人、联机器的积累，所以我们在联接技术上强力投资、实现突破，使得我们能够做到万卡级的超节点，从而一直能够做到世界上算力最强！"

这一战略可以概括为：**以更大的 Scale-Up 域补偿单卡差距**。华为不追求单芯片峰值领先，而是通过全栈自研（昇腾 NPU、鲲鹏 CPU、HCCS/UB 灵衢互联、CANN/MindSpeed/MindIE 软件栈），把更多强耦合通信保留在高带宽域内，以系统级规模优势弥补单卡不足。

### 2.3 关键突破：自研 HBM

从昇腾 950PR 开始，华为的昇腾 AI 芯片将采用**自研 HBM 高带宽内存**，解决了长期受制于韩国和美国供应商的技术瓶颈。这是昇腾 950 系列最重要的变化之一，为国内 AI 芯片自主发展奠定了供应链基础。

昇腾 950 系列基于全栈自主可控的制造工艺，搭载华为自研的第三代达芬奇架构。

### 2.4 950PR 与 950DT 的差异化定位

昇腾 950PR 与 950DT 采用共架构设计，通过搭载不同的片上内存，实现细分应用场景的竞争力提升：

| 参数 | 昇腾 950PR | 昇腾 950DT |
| --- | --- | --- |
| 片上内存容量 | 最高 128 GB | 最高 144 GB |
| 片上内存带宽 | 1.6 TB/s | 4 TB/s |
| 主要场景 | 高性能推荐、大模型 Prefill、多模态推理 | 大模型全量训练与复杂推理 |
| 定位 | 兼顾高吞吐与低延迟 | 突破内存墙瓶颈，覆盖全生命周期 |

## 3. CloudMatrix 384：当前代超节点

CloudMatrix 384（CM384）是华为超节点路线第一次较完整落地到超节点形态的代表性产品，也是理解昇腾 950 体系的基础。以下规格和数据来自公开拆解资料。

### 3.1 三层系统架构

CM384 把芯片、节点和超节点三个层级组织为同一个连续的高带宽域：

| 层级 | 组织方式 | 关键特征 |
| --- | --- | --- |
| **芯片级** | 昇腾 910C | 以达芬奇 AI Core 为核心，配套高带宽 HBM 和多路高速互联通道 |
| **计算节点级** | 8 NPU + 4 CPU + 7 个 L1 UB 交换 | 节点内形成单层 UB 平面，承担本地高带宽协同 |
| **超节点级** | 48 个计算节点 + 7 个 L2 UB 子平面 | 通过 12 个计算柜和 4 个通信柜形成二层 UB 互联 |

系统分层示意：

```
AI Core  ──片上互联/NoC──  AI Core
   │                          │
  计算 Die  ──Die-to-Die──  计算 Die
   │                          │
 昇腾 910C ──HCCS/UB端口── 昇腾 910C
   │                          │
 计算节点    ──L1 UB交换──   计算节点
(8NPU+4CPU)                (8NPU+4CPU)
   │                          │
 CloudMatrix 384 ──L2 UB+光互联── CloudMatrix 384
(48节点+7子平面)            (48节点+7子平面)
   │                          │
  更大规模集群  ──RoCE/RDMA/DCN──  更大规模集群
```

### 3.2 系统规格

| 参数 | CloudMatrix 384 |
| --- | --- |
| 计算芯片 | 昇腾 910C × 384 |
| 主机芯片 | 鲲鹏 CPU × 192 |
| 系统算力 | 约 300 PFLOPs（BF16/FP16） |
| 单芯片算力 | 800 TFLOPS 级（BF16/FP16） |
| HBM 容量 | 128 GB/芯片，系统总计 49.2 TB |
| HBM 带宽 | 3.2 TB/s/芯片，系统总计 1229 TB/s |
| Scale-Up 互联 | UB 灵衢 + HCCS |
| 单 NPU 互联带宽 | 392 GB/s 级 |
| 系统互联带宽 | 269 TB/s（双向） |
| 机柜形态 | 12 个计算柜 + 4 个通信柜 |
| 系统总功耗 | 约 559 kW |

每个计算节点由 8 个昇腾 910C、4 个鲲鹏 CPU 和 7 个 L1 UB 交换芯片组成，向上接入 7 个二层 UB 子平面，形成一对一映射关系。多柜一体化方案与单柜高密度方案相比，更强调在更大规模上维持统一的高带宽域，而不是单卡指标最大化。

### 3.3 设计哲学

CM384 与 NVIDIA GB200 NVL72 代表了两种不同的超节点哲学：

- **华为**：偏向"**规模换效率**"——以更大的 Scale-Up 域、更多芯片和更大显存总量来提升系统级有效算力
- **NVIDIA**：偏向"**单卡密度 + 高带宽交换**"——以更先进的单芯片工艺和 NVLink 高带宽交换为核心

## 4. 昇腾 950 与 Atlas 950 SuperPoD

### 4.1 昇腾 950 芯片特性

昇腾 950 是昇腾 910C 的下一代产品，于 2025 年 9 月华为全联接大会上正式发布。相比 910C，主要变化包括：

| 特性 | 昇腾 910C | 昇腾 950 |
| --- | --- | --- |
| HBM | 外购 HBM | **自研 HBM** |
| 互联协议 | UB 灵衢 1.0 | **UB 2.0（灵衢 2.0）** |
| Scale-Up 域 | 384 NPU | **千卡到万卡级** |
| 系统形态 | 超节点级 | 超节点/集群级 |
| 目标竞品 | H100/H200 | Blackwell B200/GB200 |

从昇腾 950PR 开始采用自研 HBM，是供应链自主化的关键里程碑。以下芯片级规格来自华为官方《昇腾 950 NPU 架构白皮书》。

### 4.2 芯片架构概览

昇腾 950 是一个多 Die 合封的 Chiplet 芯片，整芯片合封了：

- **2 个 AI Die**：承载第三代达芬奇架构的计算核心
- **2 个 IO Die**：承载互联通信功能
- **8 个（950PR）或 4 个（950DT）高速片上内存模块**

这些 Die 和片上内存模块通过高速 D2D Clink 和 Memory Interface 连接，整个 Chiplet 构成统一内存访问（UMA）的整体。

```
┌─────────────────────────────────────────────┐
│              昇腾 950 Chiplet 芯片            │
│  ┌──────────┐  ┌──────────┐                  │
│  │  AI Die 0 │  │  AI Die 1 │  (第三代DaVinci) │
│  │ 18 AI子系 │  │ 18 AI子系 │                  │
│  └─────┬────┘  └─────┬────┘                  │
│        │   D2D Clink  │                       │
│  ┌─────┴────┐  ┌─────┴────┐                  │
│  │ IO Die 0 │──│ IO Die 1 │  (UB 2.0 / PCIe) │
│  └──────────┘  └──────────┘                  │
│        ┌──────────────────┐                   │
│        │ 128MB L2 Cache    │  (Chiplet UMA)   │
│        └──────────────────┘                   │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────┐│
│  │片上内存0│ │片上内存1│ │片上内存2│ │ ... ││
│  └─────────┘ └─────────┘ └─────────┘ └─────┘│
└─────────────────────────────────────────────┘
```

### 4.4 关键架构创新

**第三代达芬奇架构**以 Transformer 为核心，从低精度算力、计算效率、编程易用性及系统规模等维度进行了全方位优化：

1. **Cube Core 升级**：新增 HiF8、MXFP8、FP8、MXFP4 等低精度格式，MXFP4 张量浮点峰值算力相比上一代 BF16 提升高达 **4 倍**
2. **Vector Core 优化**：从传统 SIMD 升级为双发射 Register-Based SIMD 新架构，首创 **SIMD/SIMT 混合编程模式**，FP32 与 FP16 单核算力提升 **100%**
3. **FlashAttention 加速**：通过融合 Cube-Vector 通路、增强 Softmax 效率及支持 MXFP8/MXFP4，单核性能较上一代提升 **1.5~2 倍**
4. **NDDMA 指令**：新增 N 维直接内存访问引擎，支持最多 5 维数据排布转换，硬化地址生成逻辑
5. **CV 融合通道**：Cube Core 与 Vector Core 之间的直接数据传递通道，支持随路量化与排布转换
6. **UB Memory 同步语义**：首次支持 Load/Store/Atomic 同步访存，实现最高 128 TB 的 Host-Device 及 Device-Device 内存共享

### 4.8 昇腾 950 超节点组网能力

基于 UB 2.0 互联，昇腾 950 可组建多种超节点拓扑：

| 组网方式 | 说明 |
| --- | --- |
| Full Mesh | 芯片间全互连，适合小规模高带宽场景 |
| Clos | 多级交换无阻塞网络，适合大规模扩展 |
| nD-Mesh | 多维网格拓扑，灵活均衡带宽与成本 |
| Full Mesh + Clos 混合 | 近端 Full Mesh + 远端 Clos，兼顾性能与规模 |

超节点还可构建三种资源池：

- **超大内存池**：NPU 通过 UB 端口直接访问 CPU 内存，实现高带宽低延时共享
- **超大存储资源池**：NPU 直接访问存储池，无需中间协议转换开销
- **以太互通**：通过 UB Switch 转换为以太网，或通过 UBoE 直接接入标准以太交换机

### 4.9 HiF8：华为自研低精度格式

昇腾 950 引入了华为自研的 **HiF8** 浮点格式，兼顾精度和动态范围：

| 对比项 | FP8 E4M3 | HiF8 | MXFP8 |
| --- | --- | --- | --- |
| 指数表达数 | 18 | **38** | 18（+8 位 MX 缩放因子） |
| 额外缩放因子 | 无 | 无 | 需要 8 位 MX |
| 动态范围 | 较窄 | 接近 FP16 | 较宽（依赖 MX） |

HiF8 采用变长前缀码编码的锥形精度格式：数值靠近 1 时精度高，远离 1 时精度渐变降低，综合阶码范围达到 [-22, 15]（共 38 个 powers of 2），接近 FP16 的 40 个。

## 5. 达芬奇架构回顾

昇腾 910C 及之前的芯片采用第二代达芬奇架构（详细分析见 [昇腾硬件架构](../../03算力硬件/01_npu/昇腾硬件架构.md)），昇腾 950 升级为第三代。本节对比两代差异。

### 5.1 三种计算单元

AI Core 采用达芬奇架构，包含三种基础计算资源，形成三条独立的执行流水线：

| 计算单元 | 职责 | 支持精度 |
| --- | --- | --- |
| **Cube（矩阵计算单元）** | 矩阵乘加（C=A×B+C），大模型训练/推理主力计算路径 | INT8, FP16, BF16 |
| **Vector（向量计算单元）** | 逐元素运算、归一化、激活函数、数据变换 | FP16, FP32, INT32, INT8 |
| **Scalar（标量计算单元）** | 流程控制、指令调度、地址计算 | — |

第二代矩阵计算单元：一条指令完成两个 16×16 矩阵的相乘运算（16³ = 4096 个乘加运算）。第三代 Cube Core 在此基础上新增了 HiF8、MXFP8、FP8、MXFP4 等低精度格式，MXFP4 峰值算力相比 BF16 提升 **4 倍**。

第三代 Vector Core 从传统 SIMD 升级为双发射 Register-Based SIMD 新架构，并首创 **SIMD/SIMT 混合编程模式**（以 SIMD 为主、SIMT 为辅），FP32 与 FP16 单核算力提升 **100%**。

### 5.2 存储层次

```
核外存储 (DDR/HBM)
    ↕ 总线接口单元 (BIU)
输入缓冲区 (Input Buffer) ──→ 存储转换单元 (MTE)
    │                           │ (Img2Col/转置/补零/解压)
    ↓                           ↓
 矩阵计算单元 ←──→ 输出缓冲区 (Unified Buffer) ←──→ 向量计算单元
    (Cube)           ↕                    (Vector)
                 标量计算单元
                 (Scalar)
```

达芬奇架构数据通路的特点是**多进单出**：数据流入可通过多条通路（直接到 Cube、Input Buffer 或 Unified Buffer），但所有数据输出都必须经过 Unified Buffer 才能写回核外存储。

昇腾 950 的 Memory 子系统层次：

| Memory | 容量 | 说明 |
| --- | --- | --- |
| L1 Buffer | 512 KB per AI Core | — |
| L0A Buffer | 64 KB per AI Core | Cube 输入 A |
| L0B Buffer | 64 KB per AI Core | Cube 输入 B |
| L0C Buffer | 256 KB per AI Core | Cube 输出，第三代增大以提供更灵活 Tiling |
| Unified Buffer | 512 KB per AI Core | 向量计算主存储 |
| CPU L1 Cache | 64 KB per CPU Core | — |
| CPU L2 Cache | 1 MB per CPU Core | — |
| L3 Cache | 4 MB per CPU Cluster | 服务于 AI CPU |
| **L2 Cache** | **最高 128 MB** | Chiplet UMA，支持 Cache Hint / CMO |
| 950PR 片上内存 | 最高 128 GB | 1.6 TB/s |
| 950DT 片上内存 | 最高 144 GB | 4 TB/s |

L2 Cache 的关键特性：
- 512B Cache Line，支持 4×128B Sector Cache
- 支持 L2 Cache Hint 策略（allocate / non-allocate）
- 支持 CMO（Cache Maintenance Operations）：Prefetch / Writeback / Invalidate / Flush
- 硬件维护 2 Die 间 L2 Cache 一致性，软件不感知
- 离散小包访问和随机访存场景下，同带宽条件下性能较上一代提升 2 倍以上

### 5.3 内存语义与 MTE

昇腾 AICore 目前未提供类似 GPU 的同步 Load/Store 内存语义，而是通过 **MTE（Memory Transfer Engine）** 实现远程内存访问：

- AIC/AIV 核下发 MTE 指令，通过 UB 协议访问远程 memory
- MTE 本质是异步大块数据搬移的类 Load/Store 语义，非同步语义
- 通过内部硬件流水管线实现访存和计算的异步并发

这一设计适应 AI 场景大块数据访问的特征，但与 GPU 的同步 Load/Store 语义存在差异。**昇腾 950 通过 UB Memory 弥补了这一差距**（见 [6.3 UB Memory](#63-ub-memory从异步到同步语义)）。

### 5.4 双 Die 封装

昇腾 910C 采用双 Die 封装设计，通过 Die-to-Die 互联将两个计算 Die 组合为单个芯片，在封装层面提升单芯片算力密度。昇腾 950 预计延续先进封装路线。

### 5.5 STARS 2.0 调度系统

昇腾 950 升级了第二代硬件调度器 **STARS 2.0**（System Task and Resource Scheduler）：

- Host 可下沉 2048 条任务流到 Device 侧，降低端到端调度时延
- 支持调度 AIC、AIV、CPU、DVPP、SDMA、UB、CCU 等多个引擎
- 支持并发调度最多 16 个 AI CPU 任务、64 个 Host CPU 任务、64 个 UB jetty、32 个 CCU 任务、32 个 SDMA 通道
- 使用专用高速控制总线（HSCB）与 AIC/AIV 交互，调度开销降至 ns 级
- 支持 Group 调度：AI Core 最多分 8 个 Group，支持 Die 亲和性调度
- 支持算力切分：AIC/AIV/SDMA 最多切 16 个资源池，实现虚拟机间资源隔离
- 支持实时 TOP-DOWN Profiling，记录 Task 执行时间、计算开销、带宽、功耗

## 6. 互联技术演进：从 HCCS 到 UB 灵衢

### 6.1 互联技术分层

华为超节点互联经历了从 HCCS 到 UB 灵衢的演化：

| 层级 | 技术 | 作用 |
| --- | --- | --- |
| 芯片间/板级互联 | HCCS | 昇腾早期的高速缓存一致性互联，支撑 8 卡节点内协同 |
| 节点内 Scale-Up | UB 灵衢（灵衢 1.0） | 总线级互联，支持内存语义和消息语义，单跳时延约 150-200 ns |
| 跨柜互联 | UB 灵衢 + 光模块 | 多柜计算节点组织成统一超节点，距离可扩展到 200 m 以上 |
| Scale-Out | RoCE/RDMA | 连接更大规模集群，承担超节点外的横向扩展 |
| 下一代 Scale-Up | **UB 2.0（灵衢 2.0）** | 昇腾 950 采用的新一代互联协议 |

### 6.2 昇腾 950 的 UB 2.0 互联

昇腾 950 集成了 UB 2.0（灵衢 2.0）控制器，相比上一代实现了质的飞跃：

| 特性 | 说明 |
| --- | --- |
| UB IO 带宽 | 18 Port × 112 Gbps，**2016 GB/s 双向** |
| UBoE | 2×400 Gbps，UB 协议直接接入以太网 |
| 同步语义（UB Memory） | 支持 Load/Store/Atomic，最高 128 TB 内存共享 |
| 异步语义（URMA） | 支持异步内存拷贝、Write/Read/Send/Atomic |
| 可靠传输（RTP） | 端到端可靠重传，支持 4 Port 多路径 |
| 轻量传输（CTP） | 简易传输层，支持 9 Port 带宽能力 |
| 集合通信加速（CCU） | 硬件卸载 AllReduce/AllGather/All2All 等 |
| 片上转发（UB On Chip Switch） | IO Die 内 9 Port 间流量转发，不占 DRAM 带宽 |
| 超节点规模 | 最大 **8192 卡** |
| 集群规模 | 超 **128K 卡** |
| 拓扑支持 | Clos、Full Mesh+Clos 混合、nD-Mesh |

**与 910C 的对比**：910C 的 Scale-Up 域为 384 NPU，互联带宽 392 GB/s 级；950 的 Scale-Up 域扩展到 8192 NPU，单芯片 UB 带宽达 2016 GB/s 双向。

### 6.3 UB Memory：从异步到同步语义

昇腾 910C 时代，AICore 通过 MTE 实现远程内存访问，本质是异步大块数据搬移。昇腾 950 引入了 **UB Memory 同步访存语义**，Core 可以直接向 UB 端口发起 Load、Store 和 Atomic 操作：

| 访存模式 | 910C（MTE） | 950（UB Memory） |
| --- | --- | --- |
| 语义 | 异步大块搬移 | 同步 Load/Store/Atomic |
| 操作类型 | 数据搬移 | Read/Write/AtomicStore/AtomicLoad/AtomicSwap/CAS |
| 内存共享 | 无 | 最高 128 TB Host-Device 及 Device-Device |
| 编程模型 | 需要软件管理同步 | 类似 GPU 的直接内存访问 |

这一变化使昇腾 950 的编程模型更接近 GPU 的 Load/Store 语义，降低了软件栈的适配复杂度。

### 6.4 CCU：集合通信硬件加速

昇腾 950 引入了 **CCU（Collective Communication Unit）** 集合通信加速引擎：

- 接收 STARS 调度器下发的集合通信任务，自行进行节点间数据搬运与同步
- 内置 Reduce Unit 用于数据计算，内置 MemorySlice 用于数据存储
- 通过 URMA 调用远端节点数据搬移
- 支持算法：Broadcast、Reduce Scatter、All Gather、All Reduce、All2All、All2Allv
- 实现计算与通信深度并行，释放 AI Core 算力

### 6.5 L1/L2 两级交换（CloudMatrix 384）

CloudMatrix 384 不是通过单一中心交换平面完成全部通信，而是通过 **L1/L2 两级交换与分子平面设计**：

```
                    ┌─────────────────────────────────┐
                    │       L2 UB 子平面 × 7          │
                    │  (跨柜光互联，4 个通信柜)        │
                    └────────┬────────────────────────┘
                             │
          ┌──────────────────┼──────────────────┐
          │                  │                  │
    ┌─────┴─────┐      ┌─────┴─────┐      ┌─────┴─────┐
    │ 计算节点 0 │      │ 计算节点 1 │  ... │ 计算节点47│
    │ 8 NPU     │      │ 8 NPU     │      │ 8 NPU     │
    │ 4 CPU     │      │ 4 CPU     │      │ 4 CPU     │
    │ 7×L1 UB  │      │ 7×L1 UB  │      │ 7×L1 UB  │
    └───────────┘      └───────────┘      └───────────┘
          │                  │                  │
          └──── L1 UB 交换平面（节点内）──────────┘
```

每个计算节点的 7 个 L1 UB 交换芯片分别接入 7 个 L2 子平面，形成一对一映射。这种设计把更大规模的计算资源维持在同一个低时延域中。

### 6.6 UB 灵衢的意义

UB 灵衢的意义不只在带宽或时延指标本身，更在于它把传统服务器互联提升为一种**面向 AI 计算的总线级互联**：

- 保留网络的可扩展性
- 尽量保留总线世界的低时延、统一编址和远端内存访问能力
- 支持内存语义和消息语义

### 6.7 Scale-Up 域"总线化"的最小能力集合

面向超节点的 Scale-Up 域，总线化需要以下最小能力集合：

| 能力 | 说明 |
| --- | --- |
| 寻址与权限 | UVA/IOVA/GPA 映射、隔离域、授权与回收 |
| 事务语义 | 读/写/原子（fetch-add/CAS）、完成/订购/屏障 |
| 可靠性与拥塞 | 无损要求、重传/降级策略、尾延迟控制 |
| 可观测性 | 链路/交换/端侧计数器、事件、时间戳精度 |

如果这组语义能力不能被软件生态稳定承接，硬件层面的改进就会反复转化为适配税。

## 10. 总结与展望

### 10.1 华为超节点路线的核心特征

1. **以更大的 Scale-Up 域补偿单卡差距**：384→8192→15488 NPU 级超节点将系统竞争点更多转向整域利用率而非单卡峰值
2. **全栈自研提高可控性**：昇腾、鲲鹏、HCCS/UB 灵衢/UB 2.0、CANN、MindIE 和云侧管理软件共同构成供应链与交付闭环
3. **多层总线和跨柜光互联提升扩展性**：多柜组织方式是区别于单柜超节点的重要工程特征
4. **以更高系统复杂度和功耗换取规模优势**：这也决定了它更依赖软件协同、交付工程和特定应用场景来兑现价值

### 10.2 昇腾 950 的关键意义

- **自研 HBM**：突破供应链瓶颈，实现存储自主化
- **万卡级 Scale-Up**：从 384 NPU 跃升到 8192 NPU，集群规模超 128K 卡
- **新一代互联**：UB 2.0 替代 UB 灵衢 1.0，单芯片 UB 带宽 2016 GB/s 双向
- **第三代达芬奇架构**：MXFP4 算力较 BF16 提升 4 倍，FlashAttention 单核性能提升 1.5~2 倍
- **同步访存语义**：UB Memory 实现 Load/Store/Atomic，最高 128 TB 内存共享
- **自研 Linx816 CPU**：集成华为自研 ARMv8-A 架构 CPU，支持物理双线程

### 10.3 未来挑战

| 挑战 | 说明 |
| --- | --- |
| 能效 | 系统功耗远高于竞品，数据中心供电和散热压力大 |
| 软件生态 | 编译器自动优化、算子覆盖度、社区活跃度仍需持续投入 |
| 单卡互联带宽 | 950 UB 带宽 2016 GB/s 双向，已接近 NVLink 5.0 的 1.8 TB/s 级 |
| UB 灵衢扩展性 | 扩大规模时能否维持利用率与可靠性是后续上限的关键 |
| 开发者迁移成本 | 从 CUDA 生态迁移到 CANN 生态的工程成本 |
| 950PR 内存带宽 | 1.6 TB/s 低于 910C 的 3.2 TB/s，950DT 的 4 TB/s 才完成超越 |

### 10.4 后续跟踪方向

- 昇腾 950PR/950DT 量产进度与实际性能数据
- UB 2.0 互联协议的软件承接情况与集合通信效率
- CCU 硬件卸载在实际 MoE 训练中的 All-to-All 加速效果
- UB Memory 同步语义在 torch_npu / MindSpore 中的编程接口
- 自研 HBM 的良率与产能
- Atlas 950 SuperPoD 实际部署后的 MFU/Goodput 数据
- MoE 模型在万卡级 Scale-Up 域上的通信效率
