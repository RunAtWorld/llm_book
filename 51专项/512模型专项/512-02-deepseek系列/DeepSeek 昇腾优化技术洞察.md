# DeepSeek 开源昇腾基础组件：一次把"算子生产线"搬到昇腾的全栈迁移

---

## 0. 摘要

1. **这次开源的是一整条算子生产线，不是一个模型适配结果。** TileLang（DSL）+ DeepGEMM（矩阵）+ DeepEP（通信）+ TileKernels（向量）+ FlashMLA（注意力）+ DeepSelect（筛选），与英伟达侧组件逐一对应。
2. **"逐一对应"这四个字，是整篇公告里技术含金量最高的一句。** 它把"可移植"从口号变成了可证伪的命题——只要两侧接口、语义、精度有一处不对齐，这句话就站不住。
3. **真正的门槛不在算力，在代际和规模。** 方案锁定昇腾 950 与 128 卡超节点；前者给的是低精度格式与同步访存语义，后者给的是通信域边界。两者都是硬前提，不是可调参数。

一句话概括：**DeepSeek 已经把自己的算子生产工具链做成跨后端可编译的形态，昇腾是它的第二个后端。** 这比"V4 能在昇腾上训"意义大得多。

## 1. 这件事的实质

### 1.1 交付清单

| 组件 | 公告定位 | 英伟达侧对应物 | 昇腾侧承载单元（判断） | 卡在哪条关键路径 |
|---|---|---|---|---|
| **TileLang** | 高级语言编译工具 | TileLang（CUDA 后端） | Ascend C / AI Core 全流水线 | 算子开发效率与性能上限 |
| **DeepGEMM** | 通用矩阵运算加速 | DeepGEMM（Hopper） | Cube Core + L0A/L0B/L0C + NDDMA | 训练与推理主算力 |
| **DeepEP** | 大规模跨设备通信 | DeepEP（NVLink + RDMA） | UB 2.0（域内）+ RoCE（域间）+ CCU | MoE 专家并行 all-to-all |
| **TileKernels** | 向量计算与访存算子 | TileKernels | Vector Core + Unified Buffer + MTE | Norm / RoPE / 激活 / 量化 / 排布 |
| **FlashMLA** | 稀疏注意力算子 | FlashMLA | Cube-Vector 融合通路 + 大 L2 | 长上下文注意力 |
| **DeepSelect** | 高效数据筛选 | 原栈未单列 | Vector Core | 稀疏注意力 top-k / 路由 |

### 1.2 五个关键点

**（1）"所有组件与此前面向英伟达平台的开源组件一一对应。"**
这不是套话，是一个可以被检验的技术承诺。软件栈"移植"到新硬件，最常见的做法是重写一套、接口近似；而"一一对应"意味着语义、精度、接口三个维度都要对齐。**判断：这句话是整篇公告里最硬的一句，也是后续最容易被证伪的一句。**

**（2）"TileLang 已承载 DeepSeek V4 系列模型训练中大部分算子的实现。"**
注意限定词是"训练"，不是"推理"。训练侧对数值一致性和长稳性能的要求远高于推理，所以这句话的强度高于常见的"已支持"。

**（3）"DeepSeek 训练中用到的每一个 TileLang 算子，在昇腾上都有对应的高性能实现。"**
"每一个"+"高性能"是双重限定：判据不是能编译，是**对齐手写 Ascend C 的性能**。这条如果成立，意味着编译器已经能复现专家手工调优的结果——这是 DSL 类项目最难跨过的一道线。

**（4）"在多项关键测试用例中，上述组件的计算与通信性能已接近硬件上限。"**
可量化，但公告没给口径。属**待验证**，核对方法见第 6 节。

**（5）"共同推进基于昇腾 950 的 128 卡超节点方案。"**
两个限定词都值得深挖：950 与 128 卡。它们决定了这套栈的设计边界，见第 5 节。

## 2. 为什么"一一对应"是最难的一句

### 2.1 分工边界被推到了 Infra 层

常规分工是：芯片厂给 CANN/CUDA 和基础算子，模型公司写框架层。这次 DeepSeek 把编译器、算子库、通信库三层一起交出来，等于自己站到了 Infra 层。

动因不复杂：MoE + 低精度 + 长上下文叠在一起，通用算子库覆盖不住所有性能关键路径，只能自己下场。而自研成本一旦沉没，开源就是分摊维护成本的最优解。

**判断：这不是姿态，是成本结构推出来的结果。**

### 2.2 生态的控制点在编程模型，不在峰值算力

CUDA 的壁垒从来不是 FLOPS，而是"新算子默认先写 CUDA"。谁定义编程模型，谁定义默认路径。

所以 TileLang 的看点不是语法优雅，而是它让"写一次、多后端编译"变成了可以验证的事实。公告用"一一对应"作论据，真正想证明的是：**这个抽象层没有为昇腾做功能裁剪。** 一旦裁剪，跨后端就退化成两套独立代码，可移植性主张直接失效。

> **判断**：如果 TileLang 后面开放第三方后端，它的位置接近"AI 算子界的 tile dialect"，价值随后端数量线性增长；如果长期只有 CUDA + Ascend 两个后端，它更接近"内部工具链的公开发行版"。这两条路线的差别，比这次发了什么更值得跟踪。

### 2.3 国产算力成熟度该怎么分层

拿"模型能不能跑"当判据，会系统性高估成熟度。我们内部评估应该用三层：

| 层级 | 判据 | 本次公告落点 |
|---|---|---|
| L1 可运行 | 推理链路跑通 | 早已越过 |
| L2 可训练 | 主力模型训练主路径在该栈上 | **本次落点**（V4 大部分算子） |
| L3 可开发 | 算子开发效率接近 CUDA，第三方愿意迁 | 待验证，取决于工具链 |

公告实质是宣告 L2 达成。这次开源的产业意图，是撬动 L3。

## 3. TileLang：一个刻意的取舍

### 3.1 它的抽象是什么

TileLang 是基于 TVM 的 Python 内嵌 tile 级 DSL，抽象只有四类：

- **计算域**：`T.Kernel(grid...)` 定义 CTA 级并行；
- **存储层次**：`T.alloc_shared` / `T.alloc_fragment` 显式声明片上缓冲；
- **数据搬移**：`T.copy` 描述 global ↔ shared ↔ fragment 的搬运；
- **流水与布局**：`T.Pipelined(num_stages)` 显式指定流水级数，layout 靠推断加注解。

和 Triton 的分水岭在控制权：Triton 把 layout 转换、流水调度全交给编译器，开发者只写 block 级逻辑；TileLang 把片上缓冲和流水级数**还给开发者**。

**判断：这是一次"以自动化换控制力"的主动退让。** 对昇腾来说几乎是必须的——Ascend C 的性能上限高度依赖手工双缓冲和精确的 PIPE 同步（MTE2/MTE1/M/MTE3/V 五条流水的 SetFlag/WaitFlag），全自动调度很难既通用又贴峰值。

### 3.2 "不损失硬件性能"要成立，需要三个条件

公告说 Ascend 版"对 Ascend C 底层指令进行封装、提供高级语言的编程方式、同时不损失硬件性能"。这话要成立，后端必须做到：

1. **无损 lowering**：每个 tile 抽象都映射到等价的 Ascend C 指令序列，不引入额外拷贝，不施加保守同步。
2. **布局可推导**：Cube 要 fractal 格式（zN/nZ，16×16 分形），DSL 侧是逻辑二维 tile；布局推断错一次，就多一次 transpose，性能掉一档。
3. **同步可证明**：流水级数、双缓冲队列深度、事件同步三者一一对应；错一个方向要么出数值错误，要么过度同步把吞吐等掉。

### 3.3 后端要跨的四道坎，以及 950 给了什么

| 约束 | 具体问题 | 950 的对应能力 |
|---|---|---|
| **存储层次映射** | L1/L0A/L0B/L0C/UB 六层；Cube 输出必须经 UB 才能写回（多进单出） | L0C 增大到 256KB，tiling 更灵活 |
| **数据排布转换** | 逻辑 tile ↔ fractal 的开销 | **NDDMA** 支持最多 5 维排布转换、地址生成硬件化，可把 transpose 成本压到近零 |
| **双流水协同** | Cube 与 Vector 异步，softmax 类算子要跨流水同步 | **CV 融合通道**：Cube↔Vector 直接传数据，支持随路量化与排布转换；FA 单核性能提升 1.5~2× |
| **低精度语义** | FP8 scaling 方案与 CUDA 不一致 | **HiF8**（38 个 2 的幂指数范围，接近 FP16 的 40）、MXFP8、MXFP4 |

第四道坎最容易被忽略。DeepGEMM 的核心数值方案是细粒度 per-block scaling 加两级累加，这套东西是针对 Hopper 的 e4m3 设计的。换到昇腾：HiF8 动态范围更宽，对 scaling 粒度的要求可以放松；MXFP8 的 8 位块缩放因子，又和 per-tile scaling 天然同构。

**判断：精度格式分叉是跨栈迁移里最隐蔽的成本——它不影响功能，只影响数值复现，出了问题往往在训练跑到几千步之后才暴露。**

### 3.4 它的边界在哪

TileLang 昇腾版的价值，不是"又多了一个编译器后端"，而是给 Ascend C 补了一层**性能可复现**的抽象。Ascend C 的痛点是能写但写不快，写快又依赖少数专家经验；DSL 的作用是把这些经验固化成模板和调度原语。

边界同样清楚：模型结构一旦出现全新算子形态，模板红利失效，还是得人重新设计调度。公告用"大部分算子"而不是"全部"，和这个边界是一致的——**剩下的长尾才是真成本**。

## 4. 五件套逐个拆：各自对着哪块硬件

### 4.1 DeepGEMM：主算力路径

- **原版内核**：TMA 异步搬运、warp specialization、persistent kernel、FP8 两级累加（分块累加后统一 promotion 控误差）。
- **昇腾映射（判断）**：TMA → NDDMA；warp specialization → Cube/Vector 分核与 PIPE 并行；persistent kernel → STARS 2.0 任务流下沉（最多 2048 条任务流下沉到 Device 侧，调度开销降到 ns 级）。
- **真正难的是 MoE 的 grouped GEMM**：各专家 M 维不同，要动态 tiling 加任务队列。STARS 2.0 支持 AIC/AIV 最多切 16 个资源池并发调度，正是对着这类场景设计的。

### 4.2 DeepEP：从"网络库"变成"内存语义库"

- **原版内核**：MoE expert-parallel all-to-all，两套 kernel——高吞吐（训练/prefill）与纯 RDMA 低延迟（decode），支持 FP8 dispatch，hook 机制做通信-计算重叠。
- **昇腾侧两个必要支撑，缺一不可**：
  - **UB Memory 同步访存**：950 首次支持 Core 直接对 UB 端口做 Load/Store/Atomic，最高 128TB 内存共享。低延迟 dispatch 的本质依赖 P2P load/store 加细粒度同步，而 910C 的 MTE 只有异步大块搬移语义，表达不了这个模式。**这是"必须上 950"的硬约束之一。**
  - **CCU 集合通信加速**：硬件卸载 AllReduce/AllGather/All2All/All2Allv，内置 Reduce Unit 与 MemorySlice，不占 AI Core。DeepEP 的 dispatch/combine 可以压到 CCU 上，做到真正的计算-通信并行。

### 4.3 TileKernels：Vector 侧的毛细血管

覆盖 RMSNorm、RoPE、SwiGLU、cast/量化、layout 变换这类高频零散算子。收益来自两处：

- 950 的 Vector Core 从 SIMD 升到双发射 Register-Based SIMD，支持 SIMD/SIMT 混合编程，FP32/FP16 单核算力翻倍；
- 算子融合（如 RMSNorm 叠加量化），减少 UB↔HBM 往返。

这一类最容易被低估。**经验上，训练 MFU 的差距常常不在 GEMM，而在占比 20%~30% 的零散算子有没有被融合掉。**

### 4.4 FlashMLA 与 DeepSelect：一对组合

- **FlashMLA** 打的是 MLA 的 decode 瓶颈：KV 压成低秩 latent（V2 为 512+64），各 head 共享同一份 KV，典型 memory-bound；原版在 H800 上跑到 3000 GB/s、580 TFLOPS。
- **DeepSelect** 独立成库，说明"数据筛选"已经从模型结构下沉成基础算子。结合 DeepSeek 的稀疏注意力路线（lightning indexer + top-k 选择，属判断），它干的是"先选 KV block，再让 FlashMLA 只算选中的那部分"。
- **对昇腾的意义**：长上下文的主瓶颈是带宽不是算力。950DT 的 4 TB/s 片上内存、最高 128MB L2（512B Cache Line、支持 4×128B Sector 与 Cache Hint）是这类算子的主场；950 加强的 Cube-Vector 融合通路和 Softmax 效率，直接对应 FA 类 kernel 的单核收益。

> **待观察**：稀疏注意力的收益高度依赖"选择"的召回率。如果 DeepSelect 真是和 FlashMLA 解耦的，那它也能复用到 MoE 路由、数据采样上——这是算子通用化的思路，不是给单一模型定制的补丁。

## 5. 128 卡：被一句话带过的硬边界

公告只有一句"基于昇腾 950 的 128 卡超节点方案"，但**这个数字实际上定义了整套软件栈的设计边界**。

- 950 公开的 Scale-Up 域能力远不止 128 卡（平台侧最大 8192 卡，单芯片 UB 带宽 2016 GB/s 双向，单跳时延约 150~200ns）。所以更合理的读法是：**128 卡是双方本轮联合调优的目标单元或部署形态，不是硬件上限。**
- 为什么这个规模关键：**EP 组大小直接决定 all-to-all 走 UB 还是走 RoCE。** 128 卡全在同一个 UB 域内，MoE 的 dispatch/combine 就能完全避开跨域 RDMA，延迟从微秒级降到亚微秒级——这才是"通信接近硬件上限"的前提。
- 一旦超出这个域，DeepEP 必须退回层级通信（域内 UB + 域间 RoCE），性能曲线会出现台阶。**所以 128 卡不是可调参数，是并行策略的硬边界。**

## 6. "接近硬件上限"怎么核

公告口径是"多项关键测试用例"，属于选择性披露。我们应该按四类指标自己核：

| 指标 | 核什么 | 参考线 |
|---|---|---|
| GEMM | 实测 TFLOPS / Cube 峰值（FP8、BF16 分开算） | > 80% 才叫"接近" |
| 访存类 | 有效带宽 / HBM 峰值 | > 85% |
| 通信 | all-to-all 有效带宽 / UB 单向峰值；小包延迟 | 大包看带宽，小包看延迟 |
| 注意力 | 变长、不同 context 长度下的带宽利用率 | 长序列不能掉档 |

同时要把结论拆成三层，别跨层外推：

1. **算子级对齐**（公告承诺层）；
2. **模型级 MFU**（取决于并行策略、流水、重计算）；
3. **端到端训练稳定性**（数值一致性、故障恢复、通信抖动）。

**第 1 层达成不蕴含第 2 层达成。这是跨栈迁移最常见的误判。**

## 7. 我保留意见的四点

1. **代际锁定太紧。** 公告只提 950。910B/910C 支不支持，决定这套栈的普及面——而存量最大的恰恰是 910B。
2. **双栈的数值一致性是长期负担。** 两套 kernel 要保证数值一致（FP8 累加顺序、reduction 顺序、scaling 粒度全都不同），否则训练没法跨栈复现。这个成本不会随时间消失，只会持续消耗人力。
3. **编译器长尾还没验证。** 动态 shape、变长序列、mask、稀疏索引，这四类是 DSL 后端最容易翻车的地方，也是对"每一个算子都有高性能实现"最直接的检验。
4. **性能数字全来自官方口径。** 没有第三方复现之前，"接近硬件上限"只能算待验证结论。

另外补一句"标准"问题：如果长期只有 CUDA + Ascend 两个后端，TileLang 更像内部工具链的公开发行版；要成为事实标准，得有第三方芯片厂商愿意接后端。

## 8. 趋势判断

1. **模型公司和芯片厂进入联合设计阶段。** DeepSeek 已经从算力客户变成参与定义 128 卡超节点软件栈的一方。后面头部团队的竞争力，会有一部分体现在"能不能把自家算子语义下沉进硬件"。
2. **竞争焦点从编程语言转向后端数量。** TileLang 的价值不在语法，在"一一对应"证明的可移植性。谁能做到"写一次、多后端贴峰值"，谁就掌握算子生态的分发权。
3. **Scale-Up 域变大，专家并行升为一等公民。** all-to-all 一旦能全落在 UB 域内，通信库的形态就从"网络库"变成"内存语义库"（Load/Store/Atomic 取代 send/recv）。这会反过来影响 MoE 结构设计：更大的 EP、更细的专家粒度会变得划算。
4. **低精度格式在分叉。** CUDA 侧是 e4m3/e5m2，昇腾侧是 HiF8 + MXFP8/MXFP4，动态范围和缩放机制都不一样。**跨平台数值一致性会变成一门独立的工程活**，牵扯 golden 对齐、scale 校准和误差预算。
5. **"选择"类算子独立成库，是稀疏化的信号。** DeepSelect 的出现说明注意力稀疏、MoE 路由、数据采样共享同一套筛选原语；选择从模型结构的补丁，变成了算力预算的一等变量。
6. **护城河从峰值算力转向算子覆盖率 × 开发者体验。** 硬件参数可以追，"新算子第一周就能跑出峰值"这件事追不了。

## 9. 内部分享后的行动项

1. **评估口径统一用三层法**：语言层（TileLang 后端成熟度）→ 库层（GEMM/通信/注意力覆盖率）→ 模型层（MFU）。只看"模型能不能跑"会严重高估成熟度。
2. **优先压测三类算子**：grouped GEMM（MoE）、all-to-all（EP）、变长稀疏注意力。这三类决定训练 MFU，也最容易在迁移中掉档。
3. **双回归基线先建起来**：性能基线（相对硬件峰值的百分比）+ 数值 golden（跨栈逐层比对输出）。后者是隐性成本，越晚做越贵。
4. **域大小写进集群选型指标**：Scale-Up 域决定 EP 上限，进而决定 MoE 并行策略。128 / 384 / 8192 卡是三个不同的设计空间。
5. **专项看 TileLang 的"最后一公里"**：动态 shape、调试工具、profiling。这些比 benchmark 数字更影响真实上手成本。
6. **以仓库为准，不以公告为准**：直接拉 TileLang 的 Ascend 后端和 DeepGEMM-Ascend，跑官方 benchmark，拿到自测口径再下结论。
